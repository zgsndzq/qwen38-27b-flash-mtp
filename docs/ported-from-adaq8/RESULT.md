# adaq8 — 调优结果（professorpalmer bonsai-q8-product）

测试卡：RTX 4060 Laptop 8 GB，Ada sm_89，**显存带宽 256 GB/s**（128-bit @ 8001 MHz）
对照卡：他们的 RTX 4070 12 GB @ 504 GB/s
提示词：`F:\super\adaq8\skill.txt`（中国象棋棋盘渲染器，2982 prompt token），**九个臂逐字相同**
采样：`--temp 0.6 --top-p 0.95 --top-k 20`，`-rea off`，`--parallel 1`
每臂 3 次请求 × 512 生成 token，取中位。**服务器自己的 `timings` 为准，不用客户端墙上时间。**

## 五条判决

### 1. 他们的配方赢，但只赢 **+4.8%** —— 而功劳在**接受率**，不在内核速度

`rounds/s` 在 P / T3 / T3nw 三臂之间是 **18.0 / 18.3 / 18.3** —— 几乎不动。
变的只有接受率：**0.789 → 0.823**。也就是说 q8_0 KV 和起草窗口并没有让「一个前向轮更快」，
它们让**每一轮多吃下 0.1 个 token**。

这也解释了他们 README 那句「q4_0 翻转的 top token 是 q8_0 的 12 倍」——q8_0 是**质量**决定，
速度上它与 q4_0 打平（18.01 vs 18.28 轮/s，噪声内），所以没有理由留在 q4_0。

### 2. 起草深度 3 是最优点，深度 4 是**悬崖**

从 n2 / n3 / n4 三点反推每轮成本：

| | 轮/s | 每轮 ms | 增量 |
|---|---:|---:|---:|
| n2（3 列验证 + 2 次起草） | 21.60 | 46.3 | — |
| n3（4 列验证 + 3 次起草） | 18.32 | 54.6 | +8.3 ms |
| n4（5 列验证 + 4 次起草） | 11.46 | 87.4 | **+32.8 ms** |

n3→n4 多花 4 倍，正是他们提交 `efe20ad51` 那句
**「`GGML_CUDA_PTQ1_MMVQ_MAX` 默认 4（已确认：MMQ wins from 5）」**——
第 5 列离开快速 mat-vec 路径，掉进 MMQ。**所以 n_max 必须 ≤ 3。**
（他们自己那棵树的默认 `n_max` 也正是 3；README 旋钮写 2，是保守值。）

### 3. 起草窗口 16384 是正确值，调小只亏不赚

w4k 62.17 / w8k 62.28 / **w16k 63.56**。调小窗口**省不下任何时间**（起草上下文在我们的 3.5k
深度下本来就没到窗口），却按他们文档预言的那样**掉接受率**（0.823 → 0.781）。
⇒ 保持 16384。他们那句「16k 窗口的接受数与 131k 全历史相当」在我们的卡上也成立。

### 4. ubatch 256 是对的，调大**两样都更差**

ub 512 → 60.46，ub 1024 → 56.78，而且 ub1024 的 **prefill 从 490 掉到 217 t/s**。
不改。

### 5. 我们已经在硬件极限附近，不是「没调好」

把每轮成本拆开：4 列验证 ≈ 30 ms，65 层读 5.9 GB ⇒ **197 GB/s = 卡峰值 256 GB/s 的 77%**。
再按带宽折算他们的成绩：他们的 4k 是 83 t/s，我们是他们带宽的 **0.508 倍**，
按比例应得 42 t/s —— **实测 63.6，是他们归一化预期的 1.5 倍**。

他们自己的经验值也印证：他们的 4k 效率只有 40%（带宽 504 GB/s 却只跑到 200 GB/s），
我们把 77% 花在真正读权重的地方。**剩下的差距是「每轮多吐 token」，不是「轮更快」。**

## 为什么用户实测能到 68 t/s 而这里只有 63.6

不是矛盾，是**深度**：MTP 头靠上下文预测，上下文越长接受率越高。
用户那次是 ~5960 上下文 + 生成到 2491；这里是 3.5k。按 0.823→0.90 的接受率外推：

```
(1 + 0.90×3) / (1 + 0.823×3) × 63.56 = 67.8 t/s   ← 与用户实测的 68 吻合
```

⇒ **63.6（3.5k）→ 约 68（8k）是同一条曲线上的两个点。**

## 显存怎么用掉的（视觉关掉后腾出的 ~600 MB）

| | 旧（q4_0 + 校准 + c32768） | 新（q8_0 + 分级 KV + c65536） |
|---|---|---|
| KV 精度 | q4_0（翻转率是 q8_0 的 12 倍） | **q8_0** |
| 上下文 | 32768（全显存） | **65536**（VRAM 头 24000 + pinned 主机尾 41536） |
| KV 占显存 | 576 MiB | **835 MiB** |
| KV 占主机 RAM | 0 | 1.42 GB（pinned） |
| 总显存占用 | 7251 MiB | **7673 MiB / 8188** |
| Hadamard K 旋转 | 强制关闭（校准文件要求） | **开着**（默认） |

`34.8 KB/q8_0 位置` 这个数先从他们「262144 位置 = 9.1 GB KV」反推出来，再与实测显存对上，
所以 `--kv-vram-cells` 的取值是算出来的不是猜的。

## 没动的部分（都验证过是默认最好）

- `GGML_CUDA_GRAPH_OPT=1` / `GGML_CUDA_PDL=1`：**CUDA 图是 1.5 倍的差**。关掉图后同一配置
  从 63.56 掉到 **41.28 t/s**（OPT 臂），所以这两个 env 是真金。
- MMA 解码路由（`GGML_CUDA_FA_MMA_DECODE_MIN_KV` 默认 256）、FWHT 自量化 Hadamard、
  GDN 状态 gather 融合、PTQ1_0 多列 mat-vec：源码里全是**默认开**，不需要开关。
- `-fa on`：量化 KV 的前提。
- 未采用他们的 harness-proofing（`--reasoning-effort-allow` / `--reasoning-max-tokens-floor`
  / `--jinja`）：那是给 Cline / Open WebUI 这类会发 `effort:"high"` 的客户端防 HTTP 500 用的，
  与速度无关，而我们的客户端不发。
