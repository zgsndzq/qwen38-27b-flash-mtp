# 短表（DRAFT_MAP）与中文：口径澄清 + 实测

2026-09-28。**修订版，取代同日 13:49 的那一版。**

> **修订说明**：初版标题是「短表对中文是拖慢的」，结论是 **负收益**。那个结论**建立在选错的语料上**，
> 而且**漏掉了本项目最关键的一份文献**（`qwen38mtp\docs\VOCABMAP.md`）—— 它记录了这张表正是为了修
> 「中文变慢」而被重建过的。修正后结论相反。第 6 节那个发现不受影响，仍然成立。

## 一句话结论

1. 线上这张 `shortlist_24k_mix` 对中文**是加速的**：模型自己的中文输出覆盖率 **98.9% ~ 99.8%**，
   按生成器公式 `net = gross − q` 得 **+6.4% ~ +7.5%**。
2. 「短表只覆盖了全词表汉字 id 的 5.75%」**不是缺陷**，是结构性上限（24 000 行 vs 55 328 个汉字 id），
   而且**它根本不是速度指标** —— 决定速度的是「真实文本的 token 命中率」。
3. 中文比代码慢约 30% 是**场景固有**（无短表时同样成立）。**唯一确凿的缺口**是 adaq8 少了设计里的
   自适应深度档（第 6 节）。

## 1. 短表是什么（机制）

| | |
|---|---|
| 文件 | `adaq8\maps\shortlist_24k_mix.vocab.txt`（24 000 个 token id） |
| 机制 | 草稿头 lm_head = `[5120, 248320]` = 265 MiB，**每出一个草稿 token 读一遍**；短表换成 25.6 MiB 的紧凑副本 |
| 接线 | `--spec-draft-vocab-map`；`src/llama-mtp-vocab.h` + `llama-graph.cpp:4040 build_draft_vocab_logits()` |
| 上限 | `llama-context.cpp:644` 传的是 `llama_mtp_vocab_read(file, n_vocab)` ⇒ max_size = 248320，**表长可接近全量**（header 里 32768 那个默认值被覆盖了） |
| 硬约束 | **草稿只能在表内提词，表外 token 必失**；target 全词表验证 ⇒ **输出质量零损失**，只付接受率的代价 |

## 2. 这张表有两代，线上是第二代（初版就是漏在这里）

|---|---|---|---|

## 3. 词表构成：席位是怎么分的（三个分母，别混）

脚本 `tools\_vocab_cjk2.py`（直接读 GGUF 的 `tokenizer.ggml.tokens` 逐 token 分类）：

| 类别 | 全词表 | 短表 24 000 | 选入率 |
|---|---:|---:|---:|
| ASCII | 128 062 | 20 632 | 16.12% |
| **汉字** | **55 328** | **3 181** | **5.75%** |
| 假名 / 韩 | 10 353 | 7 | 0.07% |
| 中文标点 | 234 | 41 | 17.52% |
| 其他语言 | 54 343 | 132 | 0.24% |
| special/pad | 276 | 7 | — |
| 合计 | 248 320 | 24 000 | 9.66% |

**三个不同的分母**（`tools\_verdict_cjk.py`）：

| 说法 | 分子 / 分母 | 值 |
|---|---|---|
| **中文占短表席位** | 3 229 / 24 000 | **13.45%** |
| 设计目标（VOCABMAP「~4 000 rows on talk/CJK」） | ~4 000 / 24 000 | 16.7% ⇒ **实际吻合** |
| 短表覆盖全词表 CJK id | 3 229 / 65 915 | 4.90% |
| **短表覆盖全词表汉字 id** | 3 181 / 55 328 | **5.75%** |
| 物理上限（24 000 行全给汉字） | 24 000 / 55 328 | 43.38% |

关键：**席位按语料频率买，不按词表比例分**。汉字占词表的 22.3%，但中文文本里最高频的约 3 千个 token
就覆盖了 98.9% 的 token ⇒ 「13.45% 的席位」买到「98.9% 的文本覆盖」，两者并不矛盾。
反过来，「短表覆盖词表 5.75%」这个口径**没有对应的速度含义**（设计稿 §4.5.3 自己写过：
*「注意 q 不是"覆盖率"的补数」*）。

旁证（偏代码是真的，但那是 pass 1 留下的指纹）：短表 ASCII 部分里 32.7% 是纯 `[A-Za-z]+` 单词、
25.0% 带代码标点/数字；rank 6000~6060 一整段是 `_vs` `_uint` `_perm` `_DEVICE` `_inline` `_suffix` 这类
snake_case 片段。汉字席位高度集中在前 9600 名（3 104/3 181 = 97.6%）。

## 4. 覆盖率：**必须写明语料**

分词器两条独立实现互校：自建 BPE 与 HF `tokenizers 0.23.2` 在 400 条随机中英混排串上 **400/400 一致**
（`tools\_tok_cn3.py`）。id 与 GGUF 词表对齐已逐一核对（`tools\_tok_check.py`，248 044 项 MATCH）。

### 4.1 权威语料 —— `qwen38mtp\vocab\corpus\ids`（6 074 个分词样本，就是 VOCABMAP 用的那份）

| 组 | tokens | 覆盖率 | 其中 CJK 覆盖率 |
|---|---:|---:|---:|
| `real/real/reasoning`（真实服务流量的思考段） | 41 773 | **99.83%** | 98.91% |
| `gen/zhthink/reasoning`（模型中文思考） | 8 791 | **99.74%** | 99.78% |
| `gen/zh/answer`（模型中文回答） | 29 627 | **99.31%** | 98.90% |
| `gen/zhcode/answer`（模型中文+代码） | 7 672 | 98.93% | 97.35% |
| `local/local/text`（挖掘的真实代码库） | 24 152 139 | 99.38% | 81.89% |

### 4.2 人写语料（同一张表，覆盖率能差 33 个点）

| 语料 | tokens | 覆盖率 | 其中 CJK |
|---|---:|---:|---:|
| C/C++ 源码（fork/src） | 49 065 | **99.62%** | — |
| 中文技术文档（`llm\docs` / `qwen38mtp\docs` / README / memory） | ~129 000 | **92.4%** | 82.3% |
| 中文技术笔记（`llmchat\**\*.md` 全量 165 文件） | 28 699 | **66.27%** | **48.40%** |

**为什么最后一行那么低**：`llmchat` 的笔记里混着大量**记忆饱和测试的虚构专有名词** ——
`港` 961 次、`星` 484 次、`星系`/`港口`/`领航`/`冷链`/`值守`/`报备`/`舰`/`艘`…，漏掉的 token **97.6% 是中文**，
且几乎全是这类长尾。**换一份自然中文，同一个表从 48% 跳到 99%。**

## 5. 净收益（用生成器自己的公式）

```
gross(N, depth) = HEAD_GB * depth * (1 - N/248320) / (TRUNK_GB + DRAFT_STEP_GB * depth)
net             = gross - q            # q = 1 - 覆盖率（真实 token 落表外的比例）
HEAD_GB=0.265  TRUNK_GB=5.765  DRAFT_STEP_GB=0.395  depth_code=2.657  depth_prose=2.073
```

N = 24 000 ⇒ **gross_code = +9.33%，gross_prose = +7.54%**。

| 场景 | 语料 | q | **net** |
|---|---|---:|---:|
| 代码 | C/C++ 源码 99.62% | 0.38% | **+8.95%** |
| 中文思考 | `gen/zhthink/reasoning` 99.74% | 0.26% | **+7.28%** |
| 中文对话 | `gen/zh/answer` 99.31% | 0.69% | **+6.85%** |
| 真实流量 | `real/real/*` 99.78% | 0.22% | **+7.32%** |
| 中文技术文档 | 92.4% | 7.6% | **−0.06%（保本）** |
| 长尾中文笔记 | 66.27% | 33.73% | **−26.2%** |

生成器自己的判据表（`vocab\README.md` 引 `design-vocab-shortlist.md` §4.5.3）：

| 覆盖率 | q | 结论 |
|---|---|---|
| ≥ 99% | 1% | 净 ≈ +9%，值得做 |
| ≥ 97% | 3% | 净 ≈ +7%，仍值得 |
| ≥ 90% | 10% | **保本**，危险 |
| < 90% | > 10% | **负，放弃这条线** |

⇒ **按线上表 + 模型真实产出的中文，落在第一行（+7% 档）。** 只有去覆盖「长尾虚构专有名词密集的人写文本」
才会掉到最后一行 —— 而那不是这份表被造出来要服务的分布。

## 6. 缺了一道保命闸：adaptive 档根本没有（**初版唯一的有效发现**）

设计给短表配了一个**下行地板**（`vocab\README.md`）：

> 推荐脚本用 `--spec-draft-n-min-adaptive 1`，词表再烂最多把深度压到 1，而深度 1 实测 **40.91 t/s**
> （比 `DRAFT=3` 的 39.22 还高）；target 始终全词表验证 ⇒ **输出质量零损失**。

但：

- `adaq8\llmserver.bat` 用的是 `--spec-type draft-mtp`，**不是** `draft-mtp-adaptive`；
- `grep -E "n-min-adaptive|n_min_adaptive|mtp-adaptive|MTYPE_ADAPTIVE" ada-q8/common/arg.cpp` → **0 匹配**。

⇒ 这个 fork 里**没有自适应档**。`adaq8\README.md` 写的「不用（那是主项目的自适应档）」实际是「没有」。
后果：遇到掉词多的文本，**深度仍固定 3**，三个草稿位全废还要照付草稿成本，没有回退。

VOCABMAP 的出货配置（`real=3,talk=2,code=2` 的 mix 表 **+ adaptive depth**）实测：

| 配置 | code | zh | zhcode |
|---|---:|---:|---:|
| 无短表，固定深度 3 | 40.29 | 28.19 | 37.24 |
| 仅 mix 表，固定深度 3（**= adaq8 现状**） | 45.43 | 30.33 | 35.62 |
| **mix 表 + adaptive depth（他们出货）** | 45.06 | **34.97** | **40.23** |

⇒ adaq8 在中英文上少 **~13%~15%**，就是这档的缺口。

另：**中文比代码慢 30% 是场景固有** —— 无短表那一行同样是 40.29 vs 28.19（中文草稿深度更低）。

| # | 做法 | 代价 | 效果 |

## 8. 复现脚本（`adaq8\tools\`）

```
_verdict_cjk.py   三口径（占短表 / 覆盖词表 / 上限）+ 权威语料分组覆盖率，直接算 net
_cjk_regular.py   多语料覆盖率谱（人写文档 / 笔记 / 代码），HF 官方分词器
_vocab_cjk2.py    词表构成：GGUF token 表逐 token 分类（含 GPT-2 字节映射逆变换）
_tok_cn3.py       自建 BPE vs HF tokenizers 交叉验证 + 语料覆盖率
_tok_check.py     tokenizer.json 与 GGUF 词表 id 对齐校验
```

## 9. 方法学收获（两条，值得单独记）

1. **「覆盖率」不写语料等于没意义。** 同一张表：模型中文输出 99.7% / 人写技术文档 92% / 长尾笔记 48%。
   报数字必须带语料；否则会得出方向相反的结论（初版就是这么错的）。
2. **查一个已有资产之前，先把它的完整文献读完。** `VOCABMAP.md` 就在同目录下、题名第一句就是
   *"implemented, measured, **re-mixed**"*，读完能省掉整轮误判。

> 技术坑（初版就踩过）：GGUF 的 `tokenizer.ggml.tokens` 存的是 **GPT-2 bytes→unicode 映射形式**
> （`\n` 存成 `Ċ`、空格存成 `Ġ`、`，` 存成 `ï¼Į`），而且读出来是 **bytes 不是 str**。
> 直接按码点判 CJK 会得到 **0 命中**；必须先做逆映射再解 UTF-8。
