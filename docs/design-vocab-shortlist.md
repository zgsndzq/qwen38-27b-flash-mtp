## 0. 用途定位（决定后面所有取舍）

这个模型的主要用途是**写代码**：写文章不是它的长项，也不在优化目标内。

这条定位不是"顺带一提"，它同时决定了：

1. **词表造法**：要造的是**代码高频 token 表**，不是通用自然语言高频表。
2. **保本线是否容易满足**：代码的 token 分布比自然语言集中得多 ⇒ 掉词率 q 小 ⇒ 更容易拿到毛节省。
3. **收益上限**：代码场景草稿深度更高（实测 2.66 vs 散文 2.07），而短路省的是**按步计费**的草稿头
   ⇒ **代码场景的毛节省反而比散文大**（§5.2）。用途与最优路径正好重合。

## 1. 它到底砍的是什么

MTP 草稿头 = **1 层 transformer + 共享 lm_head**。而我们的 lm_head 就是
`output.weight`，形状 `[5120, 248320]`（248320 个词），PTQ1_0 编码，**265.2 MiB**。

每出一个草稿 token 就要把 **整个 265 MiB 的 lm_head 从显存读一遍**（248320 ≫ L2，命中不了）。
而 248320 个词里，一段真实文本实际会用到的，通常只有前几万个。

短路做的事（`src/llama-graph.cpp: build_draft_vocab_logits`，qwen35.cpp:862 调用）：

```
原来：  logits = mul_mat(head[5120, 248320], h)          → 读 265 MiB
短路：  logits = mul_mat_id(head 每行当一个单行 expert, h, ids[0..n_sel-1])
                                                        → 只读 n_sel 行
        res->t_logits_ids = ids                          → 采出来的行号再映射回真 token id
```

- **不是第二份权重矩阵**（注释原话："each vocabulary row is a one-row expert of the existing head"）。
- **只作用于草稿 context**：`--spec-draft-vocab-map` 只喂给 `LLAMA_CONTEXT_TYPE_MTP`
  （`common/speculative.cpp:3461-3470`），target 仍然全词表算 —— **输出质量不受影响，只在"草稿猜不中"上付代价**。
- 草稿只能在词表内提词；target 用**全词表**验证每一个草稿 token。所以这是**有损提速但无损输出**的设计。

## 2. 我们这包为什么现在挂不上（两个硬阻断）

用最小 GGUF 读取器实读 `Ternary-Bonsai-2-27B-PTQ1_0-mtp.gguf` 得到的事实：

| 项 | 实测值 |
|---|---|
| `tokenizer.ggml.tokens` | **248320** |
| `qwen35.embedding_length` | 5120 |
| `qwen35.block_count` / `nextn_predict_layers` | 65 / 1 |
| 草稿头 | `output.weight [5120, 248320]`，`type=143` |
| 有没有独立 `blk.64.nextn.shared_head_head` | **没有**（头就是 `model.output`） |
| 头上的逐行 scale（`head_s`） | 无 |
| prism/hadamard | **有**，且 `weight_names` 里含 `output.weight` |

**阻断①：头类型不在白名单。**
`ggml.h:442` 定义 `GGML_TYPE_PTQ1_0 = 143`（"Prism packed group-128 ternary weights"）。
`llama-graph.cpp:4276 draft_vocab_direct()` 的 `switch` 只认 Q4_0…Q8_0 / Q2_K…Q6_K / IQ 系列，
**没有 PTQ1_0 / PQ2_0** → 直接 `return false` → 图里静默回退到全词表。

**阻断②：头被 hadamard 折叠了。**
`llama-graph.cpp:4305`：

```cpp
if (hadamard_rotations && hadamard_rotations->count(head_w)) {
    return nullptr;   // 短路直接放弃
}
```

而 `prism.hadamard.weight_names` 第一个就是 `output.weight`，`axis=input-last-dimension`、
`block_size=1024`、`sign_mode=explicit`。折叠后权重与激活不在同一基下，逐行取用会算错，所以作者把这条路堵死了。

**两个阻断都是"静默"的**：`build_draft_vocab_logits` 返回 `nullptr` 时只回退，不报错、不告警。
唯一的前置日志是 `MTP draft context uses the draft-only vocabulary shortlist`（`speculative.cpp:3466`），
**它只证明 map 文件被读进去了，不证明图里真的走了短路**。这一点必须在验收里单独反证（见 §6）。

## 3. 要挂上去要改什么（都是我们自己能编的源码）

**① 白名单加类型（1 行 + 白名单枚举）**，CUDA 侧已经现成：

- `ggml-cuda/mmvq.cu:275` → `case GGML_TYPE_PTQ1_0: return vec_dot_ptq1_0_q8_1;`
- `ggml-cuda/mmvq.cu:306` → `VDR_PTQ1_0_Q8_1_MMVQ`
- `ggml.c:701` → `is_quantized = true`

分发路径也对得上（`ggml-cuda.cu:2261-2266`）：`mul_mat_id` 且 `ne2(草稿行数)=1 ≤ 上限` → 走 MMVQ 单行 expert 路径。
上限取自 `get_mmvq_mmid_max_batch()`（`mmvq.cu:519`）：我们 cc=8.9 ≥ ADA → 直接返回 `MMVQ_MAX_BATCH_SIZE`，
PTQ1_0 不命中任何 `case`，走 `default` 也是最大值 —— **不会掉进需要流同步的慢路径**。

**② 把 hadamard 旋转补进短路路径（约 20~30 行）**。
关键：这个旋转**不是融进 kernel 的**，而是图内真算子 —— `llama-graph.cpp:1590-1614 build_lora_mm()` 里：

```cpp
if (t.signs) cur_mm = ggml_mul(ctx0, cur_mm, t.signs);
cur_mm = llama_mul_mat_hadamard(ctx0, cur_mm, t.rot);
// 之后才是 ggml_mul_mat(w, cur_mm)
```

所以正确做法是在 `build_draft_vocab_logits` 里**先对 `cur` 做同样的 `signs` + `llama_mul_mat_hadamard`**，
再进 `mul_mat_id` 循环。可复用同一个 `hadamard_memo`（key 已含 `cur`/`rot`/`signs`/`perm_*`）。
注意 `perm_rep > 1` 时的 reshape/permute 分支要一并照搬（我们对 `output.weight` 大概率 `perm_rep==1`，
但**不能假设**，先打印确认）。

## 4. 词表怎么造

**文件格式**（`src/llama-mtp-vocab.h:17 llama_mtp_vocab_read`）：

```
llama-mtp-vocab-v1 <n_vocab> <count>
<id0> <id1> ... <id_{count-1}>
```

约束（任一条不满足直接抛错，服务起不来 —— 这次是**响亮**失败，不静默）：
`n_vocab` 必须**等于模型的 248320**；`count` ∈ (0, n_vocab]；id 全部在 `[0,n_vocab)`、**无重复**、**无多余尾部数据**。
（错误信息里写的 `LLAMA_SPEC_CHAIN_SUB` 是文案复用，别被误导：实际 `max_size` 传的是 `n_vocab`，
即**词表上限可以开到接近全量**，尺寸完全由我们定。）

**id 从哪里来**（顺序即优先级，**口径是代码，不是通用语言** —— 见 §0 / §4.5）：

1. **代码语料为主（约 9 成权重）**：拿现成的 bat 起服务，让我们自己的模型生成一批
   **代码任务**的完整回答（含 thinking 段），同类任务重复几轮以便统计真实复用率。
   落盘 → 分词 → 数频率。这是最贴合"草稿要猜的目标分布"的来源。
   - 覆盖面要有代表性：Python / C / shell / JS 各来一批；含**长回答**（不只是短函数），
     因为长回答里的缩进、标点、惯用片段才是高频项。
2. **少量对话/指令片段（约 1 成）**：把日常真实提示算进去（提问措辞也会被草稿预测）。
3. **必须兜进去的结构 token**：EOS/BOS、chat template 的 role 标记、`\n` 与缩进变体、
   think 开关标记、常见标点与数字。
   （兜漏了不会出错 —— target 全词表验证 —— 只会在那一步拿不到草稿加速。）

**尺寸**：设成**可扫的旋钮**，准备扫 8k / 16k / 32k / 64k 四档（见 §5 的保本线）。

**自适应尾巴**：`--spec-draft-vocab-hot N` 把 map **最后 N 条**当"热槽"，运行时按"近期请求出现频率
（半衰期 8 个请求、单请求贡献上限 8、低于 0.05 剪枝）"重新指向别的 token id。
只在请求边界更新、只传 N 个 int32 —— **零图开销**。这正好补上代码里唯一的长尾类别：标识符名
（见 §4.5.2）。建议：**静态基座取 8k 代码高频，热槽留 4k**（初始填次高频），合计 **12k** ——
代码场景 8k 基座覆盖率已经很高，把余量留给热槽比堆大基座划算。

## 4.5 目标分布：代码，不是通用语言

这一节是策略修正的核心。原设计默认"通用语料"，那是错的口径 —— 我们只需要代码。

### 4.5.1 代码的 token 分布天然更集中

自然语言是长尾幂律：想覆盖 95% 要几万 token，且剩下的长尾（人名、生僻词、外来语）
永远在表外，q 随 N 下降得很慢。代码不是这个形状：

- **高频 key 是固定结构、且大多已是单 token**。BPE 对"空格 + 标识符"有专门 merge，所以
  下面的东西各自只占 **一个** token id：

  | 类别 | 例子 |
  |---|---|
  | 缩进与换行 | `\n`、`\n    `（4 空格）、`\n\t`、`\n\n` |
  | 成对符号 | `()`、`( )`、`{}`、`[]`、`(),`、`():` |
  | 运算符与赋值 | ` = `、` == `、` -> `、` += `、` >= `、` != `、` ** ` |
  | 关键字（带前导空格） | ` def `、` return `、` if `、` for `、` in `、` class `、` import `、` try:` |
  | 代码惯用片段 | `self.`、`__init__`、`print(`、`len(`、`.append(`、`range(`、`None`、`True` |
  | 注释/字符串边界 | `# `、`"""`、`', '`、`", "`、`\n\n` |

- **长尾只有一类：标识符名**（变量名 / 函数名 / 类名）。而这一类**在会话内高度重复** —— 一个
  `RingBuffer` 会在同一段回答里出现十几次。这正是下面 4.5.2 的热槽机制能自我修复的东西。

⇒ 因此预期：**同一 N 下，代码语料的覆盖率显著高于自然语言**，而且**不需要很大的 N**。

### 4.5.2 热槽 × 代码 = 绝配

`--spec-draft-vocab-hot N` 把 map 末尾 N 条当"热槽"，运行时按近期请求的出现频率重指向别的
token id（只在请求边界更新、只传 N 个 int32、零图开销）。

代码场景下这条机制的价值被放大：新标识符第一次落在表外 ⇒ 目标模型必中它（target 全词表）⇒
`llama_draft_vocab_observe` 把它记进去 ⇒ **从第二个 token 起草稿就能提它**。
即"长尾第一次 miss 之后自我修复"，而代码里长尾本来就只占很小比例。

### 4.5.3 第 1 步要测的判据（离线，不改一个字节）

拿本包模型自己生成 **代码语料**（不要混自然语言）→ 分词 → 统计频率 → 出 8k/16k/32k/64k 四张表
与覆盖曲线。然后按下表判值不值得做：

| 代码语料上 8k 表的覆盖率 | ⇒ 掉词率 q | 对照毛节省 10.0% | 结论 |
|---|---|---|---|
| ≥ 99.5% | ≤ 0.5% | 10.0% − 0.5% | **净 ≈ +9.5%，接近拿满，做** |
| 99% | 1% | 10.0% − 1.0% | **净 ≈ +9%，值得做** |
| 97% | 3% | 10.0% − 3.0% | 净 ≈ +7%，仍值得 |
| 90% | 10% | 10.0% − 10.0% | 保本，看深度自适应能否补回来（§5.3） |
| < 90% | > 10% | 负 | 放弃，转 §5.4 的其它方向 |

**注意 q 不是"覆盖率"的补数**：q 是"真实生成 token 落在表外的比例"，而覆盖率是"语料 token 落在
表内的比例" —— 两者在实测里可直接统一：**用同一份语料，既算覆盖率、又模拟草稿提词**。

## 5. 理论收益模型（按代码用途重算）

### 5.1 每轮字节账

一轮 decode 要读的字节（权重驻留显存，每轮重读一遍；`d` = 该场景的实测平均草稿深度）：

| 项 | 字节 | 说明 |
|---|---|---|
| trunk 权重 | 5.5 GB | 65 层，**每轮一遍**，与草稿深度无关（固定项） |
| target 头 | 0.265 GB | 验证 n_max+1 行是**一次** matmul，权重只读一遍（固定项） |
| 草稿每步：MTP 层 | ~0.13 GB | 1 层 + `eh_proj`，**×d** |
| 草稿每步：**lm_head** | **0.265 GB** | **×d ← 短路只砍这一项** |

实测的两个 d（本包 `ab_bench.py` 冒烟）：**代码 2.657 / 散文 2.073**。代入：

| 场景 | 基线每轮 | 其中草稿头 | 草稿头占比 |
|---|---|---|---|
| 代码（d=2.66） | 6.815 GB | 0.704 GB | **10.33%** |
| 散文（d=2.07） | 6.584 GB | 0.549 GB | **8.34%** |

换成短表（`N` 行）后草稿头按 `N/248320` 等比缩小：

```
毛节省(N, d) = 0.265 × d × (1 − N/248320) / (5.765 + 0.395 × d)
```

| 词表 N | 占全量 | **代码毛节省** | **散文毛节省** |
|---|---|---|---|
| 8k | 3.2% | **10.0%** | **8.1%** |
| 16k | 6.4% | 9.7% | 7.8% |
| 32k | 12.9% | 9.0% | 7.3% |
| 64k | 25.8% | 7.7% | 6.2% |
| 128k | 51.5% | 5.0% | 4.0% |

### 5.2 反直觉但关键：深度越高，短路越值钱

短路砍的是**按步计费**的项，而 trunk 是**每轮固定项**。所以深度越大，草稿头在每轮账里占比越高
⇒ 短路省得越多。这正好把"用途"和"最优路径"对上了：

> 我们主要用来写代码 → 代码场景深度更高（2.66 vs 2.07）→ **代码场景毛节省 10.0% > 散文 8.1%**。

同一条机制还解释了为什么"加深草稿换吞吐"是负期望（见 `BENCH.md §3.1`）：加深会让每轮验证更贵。
但在短词表这条路上，深度高反而是**顺风**。

### 5.3 下行有地板（这是敢做的理由）

**保本线**：草稿只能在表内提词，落在表外是**必失**。一阶模型下每轮产出 token ≈ ×(1 − q)，
q = 真实生成 token 落在表外的比例。所以 **q 必须小于毛节省**（详见 §4.5.3 的判据表）。

但最坏情况不会崩，因为推荐脚本 `llmserver-adaptive.bat` 用的是**自适应深度**且下限为 1：

- q 过大 ⇒ 草稿频繁失配 ⇒ 压力累加器涨 ⇒ 控制器把深度压到下限
- 深度 1 的表现 = `DRAFT=1` 档，实测 **40.91 t/s**（accept 0.750）——**比 `DRAFT=3` 的 39.22 还高**
- 所以最坏情况：**拿不到短词表的收益，但不会比现在慢**
- 而且 target 侧始终**全词表验证** ⇒ **输出质量零损失**（只需为"草稿猜不中"付代价）

⇒ 这条路的结构是「**上行 +7~9%、下行 ~0、质量零风险**」，与已落地的自适应深度正交、可叠加。

### 5.4 天花板

即使把草稿头**完全**消掉（N→0），也只有 **10.3%（代码）/ 8.3%（散文）** —— 因为：

- **target 头 0.265 GB 动不了**：采样需要完整分布，不能只算一小撮行。
- **trunk 5.5 GB 是每轮固定项**：想再往下压，只能减少**轮数**（= 提高接受率），那是另一条线。


## 6. 风险清单 / 判别法

| 风险 | 判别法 |
|---|---|
| 补丁打歪 → 图里仍走全词表（静默） | **故意造一张 512 条的极短表**：接受率必须明显崩。若数字纹丝不动 ⇒ 短路没生效 |
| `head_s` 逐行 scale 存在 ⇒ 直接放弃 | 已知我们无（`ggml_nelements(head_s)==1`），换模型要重查 |
| hadamard `perm_rep>1` 分支漏搬 | 改前先打印 `t.perm_hd/perm_nk/perm_rep` 实际值 |
| 热槽把静态高频挤掉 | 先跑纯静态表拿到基线，再开 `--spec-draft-vocab-hot` |
| 控制律耦合 | 接受率掉 → 自适应控制器降深度 → 草稿步数变少 → 毛节省缩水。两边一起看 |
| 显存 | map 本体 `n_sel×4 B`（32k = 128 KiB），可忽略 |

## 7. 执行顺序（先离线预演，再动代码）

1. **离线预演（不改任何代码，先做这个）**
   用本包 `llmserver.bat` 起服务 → 让它自己生成 **代码语料**（多语言、含长回答与 thinking 段）
   → 分词 → 数频率 → 产出 8k/16k/32k/64k 四张表 + 一张**覆盖率曲线**。
   交付物：四张 `*_vocab.txt` + 覆盖曲线 + 按 **§4.5.3 判据表**给出的"做 / 不做"结论。
   这一步把 §5 的 q(N) 从"假设"变成"实测"，**在动一行代码之前就能否决整件事**。
2. **打两个补丁 + 只重编底座**（白名单 1 行 + hadamard 约 30 行），按项目铁律抄 runtime。
3. **功能反证**：512 条极短表 → 接受率必须崩（证明短路真生效）。
4. **A/B**：`≥3 提示 × ≥3 次取中位数`，比 `tg t/s` 与接受率；先纯静态扫表长，再加热槽。
5. 有效才固化成 `llmserver-vocabmap.bat`（生产 bat 不动），并把结论写回 Runbook。
