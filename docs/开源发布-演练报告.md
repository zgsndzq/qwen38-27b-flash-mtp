# 开源发布演练报告

**日期** 2026-10-15　**目的** 用一个独立目录模拟真实使用者，验证"只下载、不编译"和"下载源码、自己编译"
两条路都能跑起来，并把发布物缺的东西暴露出来。

**状态**：两条路径均通过；发现的 9 条内部痕迹**已全部修复并复验**；剩余 3 条待办在文末。

---

## 一、演练怎么搭的

模拟**三个发布渠道** + **一台干净的用户机**：

| 模拟物 | 对应真实渠道 | 内容 | 体积 |
|---|---|---|---|
| `_release_out\hf-model\Ternary-Bonsai-2-27B-PTQ1_0-GGUF\` | Hugging Face model repo | 6 个 gguf + model card + `SHA256SUMS` | 29.4 GB |
| `_release_out\github-src.git\` | GitHub 源码仓 | `git clone --bare` 出来的裸仓 | 349 MB |
| `_release_out\releases\` | GitHub Releases | `ada-ternary-win64-sm89-<commit>.zip`、`ada-ternary-src-<commit>.zip` | 603 MB |
| **`duan\`** | **用户机** | 只从上面三处"下载" | — |

用户机的最终形态：

```
duan\
├── ada-ternary\               ← Release zip 解包
│   ├── build\bin\  build\cuda\        预编译二进制 + CUDA 运行时
│   ├── weights\                       从 HF 下的 gguf
│   ├── maps\  llmchat\               草稿短名单 + 客户端
│   └── llmserver.bat  features.ini  README.md
└── code\                      ← GitHub clone 的源码（场景 B 用）
```

> 权重用**硬链接**而非真拷贝：路径与目录项完全独立，但省掉 29 GB 和十几分钟复制。
> 真实使用者走 HF 下载，这是唯一的简化点。

## 二、结果：两条路都通

### 场景 A —— 只下载，不编译 ✅

```
1) 解压 ada-ternary-win64-sm89-eea905c8.zip                    (4 s)
2) 从 HF 目录取 6 个 gguf 到 ada-ternary\weights\
3) 双击 ada-ternary\llmserver.bat

    ada: feature file features.ini -> 11 applied, 0 ignored
    MTP draft context uses the draft-only vocabulary shortlist 'maps/shortlist_24k_mix.vocab.txt'
    load_model: loaded multimodal model, '...\weights\mmproj-...gguf'
    llama_server: listening on http://127.0.0.1:18080

    3 次请求全部正常出码：54.2 / 70.8 / 77.4 t/s
    包内客户端 llmchat\chat.py 也正常连上（服务端模型 Ternary-Bonsai-2-27B）
```

整条链路**零绝对路径** —— `llmserver.bat` 全靠 `%~dp0`，`--features-file features.ini` 靠首行
`cd /d %~dp0` 定位。zip 里带了 CUDA 运行时，所以用户**不需要装 CUDA Toolkit**。

### 场景 B —— 下载源码，自己编译 ✅

```
1) git clone github-src.git  ->  duan\code
2) copy build.local.example.bat build.local.bat   然后填 6 个值
3) _build_q8.bat

    560/560 目标   CFG_EXIT=0  BUILD_EXIT=0  SERVER_OK  DONE     (约 20 分钟)
    源码路径确认是 F:/super/duan/code/...（用的是用户自己的树）

4) 产物覆盖到 ada-ternary\build\bin\ 再启动 -> 正常，71.4 / 67.5 / 80.6 t/s
```

**缺 `build.local.bat` 不会静默出错** —— 脚本写 `MISSING build.local.bat` 并退出（码 9），
不会在别处乱建目录。

自编译产物 vs Release 二进制的 sha256 全不同（编译路径与时间戳嵌进二进制），但行为一致 —— 正常。

## 五、剩余待办（不影响"能不能跑"，影响"能不能发"）

| # | 事项 | 为什么必须处理 |
|---|---|---|
| B1 | **源码仓是 shallow 的** —— 11016 个提交，边界 `f4f7758ca` | 发布前 `git fetch --unshallow`（需代理，几百 MB）。不影响编译，但开源仓应该是完整历史 |
| B3 | **model card 的 base model 与许可证填不了** —— gguf 元数据里没有 `license` / `author` / `base_model` 字段（只有 `general.name = Swift-Bonsai-2-merged-PTQ1_0`、架构 `qwen35`） | 这是**衍生模型**，许可跟随 base，不能声明为原创。必须人工确认上游仓库与许可证 |
| B4 | 仓库里没有 `LICENSE` 文件 | 补一份（MIT，同上游），并在 README 里指明 |
| — | 建 org、把 `code\` 推上 GitHub、HF 建 repo 上传 | 基础设施动作，脚本之外的活 |
| — | `palmer/prism` 那条引用落后上游 63 个提交 | 公开仓上的 `prism` 已经不是真上游，别人会 clone 到错的东西 |

**环境的坑（记录，不是发布物的问题）**：在 agent 会话里 `shutil.rmtree` 会被安全层重定向到回收站，
大目录（数千文件）会失败，得改用同盘改名。这也是 `simulate_user.py` 重跑时会先失败一次的原因。

## 六、结论

**技术条件已具备**：两条使用者路径都在独立目录里跑通了，运行侧零外部依赖，
构建侧靠一份 `build.local.bat` 就能适配别的机器。

**第一次演练暴露的 9 条内部痕迹已全部清掉**，复验确认：文本零泄漏、日志标签中性、
私人数据不再随包分发。剩下 3 条（shallow 历史、许可证、LICENSE 文件）是**行政动作**，
不是技术障碍 —— 但**许可证那条不解决就不能发**。

**下一步**：`git fetch --unshallow` → 确认 base model 与许可证 → 建 org / HF repo → 上传。
