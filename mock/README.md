# mock/ —— 不编译 CUDA 先把账算清

写内核之前回答两个问题，顺序不能反：

1. **值不值得**：加宽/改树能拿多少收益（只看 acceptance，与 kernel 无关）
2. **做不做得成**：寄存器 / SMEM / occupancy 在哪一档崩

## 目录

| 文件 | 作用 |
|---|---|
| `params.json` | 全部输入参数（硬件、草稿分布、树形状、轮数）。改这里，不改代码 |
| `sim_tree.py` | **蒙特卡洛**：真逐轮抛硬币，统计 gain 分布和 tok/s。支持 1e6~1e7 轮 |
| `sim_matvec.py` | **解析模型**：ncols × nrows 参数空间的寄存器/SMEM/occupancy 扫描 |
| `calibrate.py` | 从 `src/logs/server.log` 提取真实 acceptance，写回 `params.json` |
| `results/` | 每次跑的 JSON 快照 |

## 时间预算：任何模拟都不许超过 60 秒

实测耗时（本机，numpy 向量化）：

| 轮数 | 实际耗时 | 用途 |
|---|---|---|
| 100k | 0.6 s | 改完代码先验语法/逻辑 |
| 1M | **1.2 s** | 默认值，结论已收敛 |
| 10M | 7.4 s | 最终数字 |

真要超时用 `--force`。

所以除非推翻假设，不需要跑 10M 以上。

## 当前结论

### 链式加宽 = 白做

`sim_matvec.py` 的输出：链式的收益天花板是 `1/(1-α)`，n=5 时已经吃掉 87%。

| α | n=5 → n=48 的增益 |
|---|---|
| 0.40 | +0.0% |
| 0.60 | +0.4% |
| 0.75 | +2.3% |
| 0.90 | +8.4% |

而且 48 列时寄存器 143、每 SM 只剩 1 个 block（occupancy 17%），实测预测 **40.9 t/s，
比现在的 92 还慢**。**加宽链式这条路可以直接划掉。**

### 树式有效，但幅度取决于候选分布

48 节点预算，1M 轮蒙特卡洛：

| α | geometric（独立假设） | zipf s=1.1（长尾，保守） |
|---|---|---|
| 0.44 | **4.16×** → 337 t/s | **1.43×** → 116 t/s |
| 0.60 | **3.80×** → 402 t/s | **1.37×** → 145 t/s |

基线是现在的链式 n=5（约 106 t/s）。

**两个模型差 2.8 倍**，所以真值在 1.4× ~ 4.2× 之间，**中位预期约 2×**。

但不管哪个模型，**树都远好于"加宽链式"（+0.4%）**，这个结论不受假设影响。

### 内核侧

同样 48 列预算，`sim_matvec.py` 显示寄存器 143 < 255（不溢出），
瓶颈在 occupancy：每 SM 1 个 block。带宽受限内核在 17% occupancy 下可能仍能打满，
但需要实测确认——这是唯一需要编译验证的点。

## 已知局限（重要）

1. **实测样本只有 1 轮**。`calibrate.py` 从 server.log 解析到
   `mean len 1.77 → α≈0.435`，但那是冷态（ngram 表空）的一次冒烟，
   不足以代表分布。要可靠标定，需要跑一条长回答（50–200 轮）再 `calibrate.py --write`。
2. **两种分布模型都是猜的**。geometric 偏乐观（候选独立），zipf 偏保守（纯长尾）。
   真实的 top-W 覆盖要靠 drafter 的实际 logits 统计，不是拍参数。
3. **树的每层命中率按 `decay^k` 平衰落**。真实 EAGLE 树越深衰减越快（非线性），
   所以 zipf 那档可能还不够保守。
4. 模拟假设一次前向能验证全部 48 个节点且权重只读一次——这要求内核改造成功，
   是模拟的**前提**而不是结论。

## 标定：200 轮真实生成要多久

一轮 = 一次投机步（4 草稿 + 1 验证），产出 `1 + mean_len` 个 token。
α=0.6、n_draft=4 时 `E[len] = 1 + a + a² + a³ + a⁴ ≈ 2.31`，所以 200 轮约 **460 token**。

| 轮数 | 产出 token | 46 t/s（BENCH，最慢） | 100 t/s | 177 t/s（ngram 热） |
|---|---|---|---|---|
| 200 | ~460 | **10.0 s** | 4.6 s | 2.6 s |
| 500 | ~1150 | **25 s** | 11.5 s | 6.5 s |
| 1200 | ~2770 | **60 s（上限）** | 28 s | 15.6 s |
| 2000 | ~4600 | 100 s ✗ | 46 s | 26 s |

交叉验证：每轮一次权重读取 = 5.79 GB / 272 GB/s = **21.3 ms** → 46.9 轮/s，
与上表 46 t/s × 2.31 token/轮 自洽。

**结论：200 轮 3–10 秒，500 轮也只要 6–25 秒，60 秒预算能装下 1200–4000 轮。**

样本量够不够：200 轮的 mean_len 标准误约 ±0.09（len 的 sd≈1.3），
换算到 α 约 **±0.02–0.03**——判断"α 是 0.44 还是 0.6"绰绰有余。
但**判断不了 geometric 还是 zipf**：那是候选概率的**分布形状**，200 轮的
总体 acceptance 里含不下这个信息，需要按草稿深度分别计数（当前日志没有）。

## 逐层存活曲线：把"猜形状"换成"量形状"

**已经接好了**，不需要额外改代码：

1. `server-context.cpp` 里 `acc per pos` 从 `SLT_TRC` 提到 `SLT_INF`，
   默认 verbosity 就进 `server.log`，并且多打了 `steps = N`（加权用）。
2. 那一行是**累积存活函数** `S(i) = P(len > i)`，因为底层计数器是累积的
   （接受 k 个 token 会把 0..k-1 全部 +1）。第 i 层的边际命中率 = `S(i)/S(i-1)`。
3. `calibrate.py` 自动解析、加权、算边际，并做**形状判定**。

判定逻辑不是"哪个族拟合更好"，而是**边际是否恒定**——geometric 的充要条件就是
`p_i` 不随深度变（边际比全 1）。实测边际明显衰减时，两个族都不对，
此时唯一诚实的做法是用实测序列，所以 `--write` 会直接写 `model="empirical"`。

新增第三种模型 `empirical`：直接用 `draft.per_depth` 里的实测边际，
深度不够时按最后一个比值外推。它比 geometric / zipf 都更接近真值——后两者本来就是我们猜的。

```bash
# 跑完一条长回答后
$PY mock/calibrate.py                      # 先看判定，确认边际比是否稳定
$PY mock/calibrate.py --write               # 写 per_depth + model=empirical
$PY mock/sim_tree.py                        # 用实测形状重跑
```

用合成日志验证过判定（`mock/results/_selftest/`）：

| 真值 | 边际比均值 | 判定 | 结论 |
|---|---|---|---|
| 恒定 0.6 | 1.001 | geometric | alpha=0.600 |
| 0.6/0.35/0.15/0.05 | 0.476 | 长尾 | 必须 empirical |

同一份 1M 轮模拟里，两种形状的差异是实打实的：

| per_depth | 最优 width | gain |
|---|---|---|
| 0.6×4（恒定） | 4 | **4.69×** |
| 0.6/0.35/0.15/0.05 | 8 | **2.14×** |

注意长尾的最优解是**更宽更浅**（width=8、depth=6），恒定才是 width=4、depth=12。
所以形状不只影响收益大小，还影响**树该长什么样**——这就是必须量的原因。
