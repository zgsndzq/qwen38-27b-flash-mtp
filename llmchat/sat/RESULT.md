# 记忆饱和测试：条数到底有没有上限？

**结论先说：上限就是 ctx 长度，不是注意力。在 ctx 装得下之前，加记忆不损失任何一条的召回。**

跑法：`mem` 里有几个文件就注入几个（全量、无匹配），用 JEV 判据题读正确项的归一化概率 p。

- **虚构事实**：160 个虚构星港 / 8 张虚构卡片，编号模型先验里不存在 ⇒ 答对只可能是"读到了记忆"。
- **文件严格嵌套**：N=4 的 4 个文件就是 N=8 里的前 4 个 ⇒ 同一条记忆在各档之间字节一致。
- **判据题的选项位置**按域号固定打乱，避免"正解全在 A"的位置偏差。
- 服务：`llmserver.bat`（带 mmproj），ctx **16384**，`cache_prompt=False`（每次全量 prefill）。

## 四条结论

1. **没有"越多越错"。** 从 1 条到 128 条，单条召回一条都没掉。用户"记忆宁可多不能少"的直觉在这条轴上成立 —— 加记忆是免费的（代价只是 ctx 和 prefill 时间）。

2. **上限 = ctx / 单条成本。** 文本约 **130 条**，图片约 **60 张**（16384 ÷ 250）。想装更多，只能加 ctx（吃显存），不是"注意力会崩"。

3. **单条成本（实测）**：文本 **125 token / 168 字符**；图片 **250 token / 张**（600×400）。⇒ 规划记忆库时按这个折算。

4. **位置影响存在但很小**，且不随 N 放大。同一道题（D32）在 32/64/96 条下 p = 0.872 / 0.864 / 0.893 —— **完全平**，既没有"中间被淹没"，也没有深度衰减。

## 付钱的另一头：prefill 时间（cache_prompt=False 的实测）

| N | 单次请求耗时 |
|---:|---:|
| 1 | 0.6 s |
| 32 | 8.4 s |
| 64 | 16.7 s |
| 128 | 34.4 s |

线性 ≈ **0.25 s / 条**。真实使用中记忆块每轮位置都在变（它在问题之后），**未必能命中 prompt cache** —— 这条还没测，是下一个该验的点。

## 还没测的

- **图片轴到 ctx 边界**（只跑到 8 张，够证明无衰减，但没逼出上限）。
- **多轮缓存行为**：记忆块在问题之后，每轮位置不同，可能每轮都要重新 prefill。要看 `timings.cache_n` 才知道。
- **生成质量而非召回**：这里测的是"能不能精确取到某一条"。用户担心的"做多了输出乱"属于生成侧，需要单独的生成类评分。
