# 记忆的索引与图 —— 设计稿

> 2026-09-26。前提判决：**不存在"能提升记忆的模式"**。唯一机制是把 token 放进上下文，
> 所谓"文本记忆 / 视觉记忆 / 混合"只是"放什么字节"。真杠杆只有三个：
> **① 选择（索引）② 组织（图）③ 冗余（同一事实多条覆盖路径，已定论）**。
> 本文只讨论 ①②。
>
> ⚠️ 本文档**不要**放进 `mem\`（那里任何 `.md` 都会被当记忆自动注入）。

---

## 0. 现状盘点

`llmchat\chat.py` 现在的行为是：`mem\` 下**有什么就全量注入什么**。

- 没有命中判定、没有排序、没有预算控制 —— 关键词匹配在库里只有 1 条时被主动删掉了（只会漏，没有收益）。
- 这在**小库**下是**最优**的（不漏召回）。库一大就爆上下文，最差的情况是把 prompt 挤出去。
- ⇒ 索引的价值 = f(库规模 / 上下文预算)。**拐点才是该上索引的时刻**，之前上只会引入漏召风险。

---

## 1. 索引：怎么让提示词命中记忆

### 1.1 ⭐ Skill 为什么感觉更好 —— 它自带索引层

用户反馈"效果不如 Skill 的模式"，除了自然语言本身（见 `memory-quads-inject` 技能），
还有一个结构性原因：

```
Skill  =  正文（按需加载）  +  name/description（常驻，决定"何时该加载"）
我们   =  一整个文件全量塞进去，没有上面那一层
```

**Skill 天生带一个索引层**：`description` 常驻上下文、正文按需读入（渐进式披露）。
我们把记忆做成一个文件全量注入，等于把 Skill 的索引层扔掉、只留正文。

⇒ 要复刻的正是这一层：**目录常驻、正文按需**。

### 1.2 方案谱（按成本排，别跳级）

| | 方案 | 成本 | 什么时候用 |
|---|---|---|---|
| A | **全量注入**（现状） | 0 | 库小（mem 总量 ≲ 2~4k token） |
| B | **词面命中**：字符 2-gram / 实体名 | 极低，纯 Python | 库中（几十~几百条） |
| C | **分层披露**：目录常驻 + 命中后加载正文 | 低；多一次往返 | 库大，或想让模型自己决定要哪条 |
| D | **向量检索** | 中（需要 embedder） | 词面命中不够时 |
| E | **训出来的路由器** | 高（要数据、要训、要评） | 库很大、或对精度要求高 |

- 中文不需要分词器：**字符 2-gram** 的检索质量已经很高，且零依赖。
- D 的硬约束（写在项目记忆里）：**`--embeddings --pooling mean` 与 MTP 互斥**，
  且**同卡严禁两个 llama-server** ⇒ 向量检索要么**离线建索引**，要么另起一个**独立的小 embedder**（CPU，几十 MB 级）。
- **别跳级**：A→B 的收益要等库变大才出现；提前上 D/E 是拿工程复杂度换不存在的收益。

### 1.3 命中判定要"概率"不要"是/否"

我们已有的 JEV 机制（`max_tokens:1 + logprobs + top_logprobs`）本质就是
**一次前向拿到候选概率**。把候选项从"选项 A/B/C/D"换成"该加载哪几条记忆"，
就得到一个**概率化索引**：阈值 + top-k，而不是硬命中。

- 优点：能拿到"这条记忆要不要给"的连续置信度，可以对同一实体取前 k 条（正好配合冗余结论）。
- 代价：一次全前向（实测 0.5 s 量级）⇒ 只适合库大、每次必须选的时候，不能每条都判。

## 2. 图：记忆里的知识如何成图

### 2.1 三层图，别混为一谈

1. **显式图** —— 我们写在文件里的（实体 + 引用）。
2. **隐式图** —— 模型读进去时**自己建的**（注意力边）。
3. **训练出的图** —— 落在权重里的。

这三层的分工是本文最重要的结论：
**知识不该训练进权重（主干三值 PTQ，合并式改动要回 BF16 母版 54 GB）；
权重里的"图"只该用来做检索。**

### 2.2 ⭐ 图主要不是"我们画"的，是"注意力自己建"的

模型读自然语言时，**同一实体的每一次出现都会建立注意力边**。我们要做的不是把图写出来，
而是**让这些边连得上**：

- 反例（四元组）：`将` 和 `(4,0)` 分别落在两行，中间隔着竖线和别的 token
  ⇒ 边被拉长、被稀释，图**更难建立**。
- 正例（自然语言）：同一段里 `将`、`(4,0)`、`九宫`、`中线`、`上方底线` 反复共同出现
  ⇒ 边又多又短。**这也就是自然语言赢的第三个机制。**

### 2.3 可立刻执行、零成本的第一动作：命名一致 + 就近共现

**同一实体只用一个名字**，且把它相关的属性写在同一段里。

- 不写 `将` / `將` / `帅（黑）` 混用 —— 每一次换名字都在**切断一条边**。
- 数值和它描述的对象要贴着写，不要拆到两张表里。
- 这一条不花钱、不改代码，直接决定隐式图的质量。

### 2.4 显式图怎么自动化（不需要模型）

- 每一条记忆块给一个 **id**；`mem\` 里的文件 = 记忆块集合。
- **抽实体**：域内实体是**坐标** `(x,y)`、**棋子名**、**区域名**（九宫/河界/x3-x5）—— 规则足够，
  不需要 NER、不需要模型。
- **连边**：同块内共现 + 显式交叉引用（正文里写"见 河界"）。
- **产物** `graph.json`：`实体 → [块 id]`，以及 `块 → [邻居块]`。
- **用法**：命中 1 条 → **沿图把邻居块一起注入**。这就是**把"宁可多不能少"自动化**：
  先精确定位（不浪费），再按边扩展（不漏）。

### 2.5 训练：只训路由器，不训知识

- 要训就训**命中判定器**（prompt → 该加载哪些块）。它小、可训、可评、可回滚。
- **数据自举**：每条记忆块生成 5~10 种问法（正样本），跨块问法当负样本。库有了就能训，不用外部数据。
- **目标**：同一条记忆的不同问法在表示空间靠近（对比学习）——本质是 Word2Vec/GNN 那套，
  但落点是**检索**，不是生成。
- ❌ 不训生成器；❌ 不把知识写进权重；❌ 别在库只有个位数条目时就开训（没有负样本空间）。

## 3. 怎么验（指标要对得上目标）

| 目标 | 指标 | 对照 |
|---|---|---|
| 索引选得准不准 | **Recall@k**：库 N 条、问 M 题，注入 k 条时的命中率 | 全量注入（上界） |
| 索引划不划算 | 注入的**无效 token 数** | 全量注入 |
| 图连得对不对 | **多跳题**：答案需要 A+B 两条记忆 ⇒ 注入 {命中条} vs {命中条 + 图邻居} | 已测过同类：推理组 0.431 → 0.713（**乘性受益**） |
| 什么时候必须索引 | 库增长时的 Recall / 延迟曲线 | 拐点 = 该上索引的规模 |

**验收底线**（沿用项目铁律）：每题要能自动判对错；必须有 off 基线同题对照；
同配置同会话、≥3 次取中位（同配置散布 ±12%）。

---

## 4. 建议的最小下一步（按顺序，别并行）

1. **命名一致化**（0 成本）：把记忆文档里同一实体的写法统一，相关属性就近成段。先造边。
2. **加目录层**：每条记忆块头一行写 `id | 一句话说这是什么`；客户端先只注入目录，
   由规则（或模型一次判定）选择要加载哪几条。**这一层就是 Skill 的 `description`。**
3. **凑库到 20~50 条**（用现有棋盘 + 再复制两个域），量 **Recall@k**，跟全量注入对照。
   库不够大时，索引看不出收益——这是先有鸡还是先有蛋的问题，必须先把库做起来。
4. 库过几百条，再谈**向量检索**与**训路由器**。
